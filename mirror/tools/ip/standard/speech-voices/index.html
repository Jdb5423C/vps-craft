Web Speech API 语音指纹：为什么「检测到中文语音」大多数时候是误报

解析现代浏览器如何通过 window.speechSynthesis.getVoices() 枚举宿主系统的 TTS 发音人，以及一个被大量脚本写错的判据：必须区分『本机离线引擎』（localService === true，如 Windows 的 Huihui / Kangkang）与『浏览器云端语音』（如 Edge 的 Microsoft 晓晓 Online (Natural)，任何装 Edge 的机器都会列出）。只有前者是弱信号，后者不构成任何地域特征，误判会冤枉大量干净的美国家宽用户。

一、 隐蔽的刺客：Web Speech API 是如何出卖你的宿主环境的？

当绝大多数开发者在防范反欺诈与浏览器指纹追踪时，往往只把注意力放在 IP 地址、DNS 泄漏、时区（Timezone）以及浏览器的 User-Agent 上。很多人以为：“只要我把 macOS 或 Windows 操作系统的显示语言换成 English (United States)，浏览器首选语言也改成 en-US，再加上纯净的美国家庭宽带代理，Anthropic 和 Cloudflare 就绝不可能知道我是中国用户。”

然而，现代 HTML5 规范引入了一套看似极其人畜无害、旨在提供无障碍辅助和文本转语音能力的系统级接口 —— Web Speech API（特别是其子模块 SpeechSynthesis）。

这套 API 确实能枚举发音人列表，但「能枚举」不等于「能定位」。列表里混着三类东西——浏览器云端语音、操作系统内置语音、用户主动安装的离线引擎——只有最后一类带有哪怕一点点地域信息。判断依据是每个 SpeechSynthesisVoice 对象上的 localService 属性：false 表示由服务器合成，true 才是本机磁盘上真实存在的引擎。

// 异步枚举宿主机安装的所有 TTS 发音人
const synth = window.speechSynthesis;
let voices = synth.getVoices();

if (voices.length === 0) {
  synth.onvoiceschanged = () => {
    voices = synth.getVoices();
    console.log("探测到的系统语音包总数:", voices.length);
    console.table(voices.map(v => ({ name: v.name, lang: v.lang, localService: v.localService, default: v.default })));
  };
} else {
  console.table(voices.map(v => ({ name: v.name, lang: v.lang, localService: v.localService, default: v.default })));
}

当这段脚本在你的电脑上执行时，哪怕你的 Chrome 界面是纯正的美式英语，你的控制台依然会输出如下带有明显地域烙印的语音包列表：

  • Ting-Ting (zh-CN) —— macOS 经典普通话发音人
  • Sin-ji (zh-HK) —— macOS 粤语发音人
  • Mei-Jia (zh-TW) —— macOS 台湾国语发音人
  • Microsoft Xiaoxiao Online (Natural) - Chinese (Mainland) (zh-CN) —— Windows 现代高拟真神经发音人
  • Microsoft Yunxi Online (Natural) - Chinese (Mainland) (zh-CN) —— Windows 常用男声语音包

二、 风控视角：原生海外环境与中文环境的真实差异

为了理解这一项为什么只值 10 分（而不是很多脚本里写的 15 分甚至更高），需要先看清一个关键区分：浏览器能列出的语音，绝大多数并不来自本机。

桌面版 Edge 会把微软 Azure 认知服务的整套云端语音注入 speechSynthesis——中文的晓晓、云希、云健，英文的 Aria、Guy，加起来两百多款。这些语音的 localService 属性是 false，意思是它们由服务器合成，本地磁盘上并没有对应引擎。一台在俄亥俄州买的、从未装过中文的英文 Windows，只要打开 Edge，同样能列出这一整套中文发音人。

同理，macOS 的 Ting-Ting、Mei-Jia、Sin-Ji 随系统预装，与购买地、系统语言、Apple ID 区域都无关。真正能反映"这台机器装过中文环境"的，只有 localService === true 且不属于系统内置的那一小撮离线引擎——比如 Windows 中文语言包带来的 Microsoft Huihui Desktop、Kangkang。

为什么这一项只能算弱信号

  1. 云端语音零信息量： Edge 的 Online (Natural) 系列对所有用户一视同仁，不同机器之间几乎没有差异，风控无法据此区分国家。
  2. 系统内置语音同样是基线： macOS 的全语言语音库只能说明系统自带，不能说明用户在哪。
  3. 真正的信号范围很窄： 只有本机离线引擎的命中与否带一点点信息量，与出口 IP 类型、时区、DNS 这些强信号相比，权重低一个数量级。

把它写成「一锤定音的物理机铁证」，是把系统的兼容性设计误读成了地域特征。

三、 深度技术剖析：操作系统是如何把语音包注入浏览器的？

为什么浏览器插件（如通常的代理切换器、甚至很多所谓的指纹伪装插件）无法有效防御 getVoices() 测绘？

这是因为 Chromium 和 WebKit 架构对 Web Speech API 的实现并非纯前端沙盒运算，而是直接通过 IPC 管道向宿主系统的多媒体服务发起异步 IPC 探测：

1. macOS 平台架构（AVFoundation）

在 macOS 下，WebKit 和 Chrome 通过 AVFoundation 的 AVSpeechSynthesisVoice.speechVoices() 向系统查询发音人列表。这里有一个常被忽略的事实：macOS 的语音库本身就是全语言的。/System/Library/Speech/Voices 下的 Ting-Ting、Mei-Jia、Sin-Ji、Yu-Shu、Li-Mu 在任何一台 Mac 上都存在，与系统语言、Apple ID 区域、购买地都无关，而且受 SIP 保护无法删除。用户能下载和删除的只有「增强型 / 高品质」语音包。

2. Windows 平台架构（SAPI 与 Windows.Media.SpeechSynthesis）

在 Windows 10/11 下，Edge 和 Chrome 底层对接的是 Speech API (SAPI 5.3+) 以及现代 UWP 命名空间 Windows.Media.SpeechSynthesis。Windows 会遍历注册表项：

HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Speech\Voices\Tokens

由于国内绝大多数 PC 品牌出厂搭载的都是“家庭中文版”或通过中文 ISO 镜像安装的系统，即使后来通过语言包补丁切换了 English 显示语言，该注册表项下残留的 Huihui、Kangkang、Yaoyao 等键值依然存在且处于激活状态。这类本机离线引擎才是这一项唯一有效的信号——注意要和 Edge 注入的 Online (Natural) 云端语音严格区分，后者在 getVoices() 里同样会出现，但 localService 为 false。

四、 自动化检测逻辑：Claude 与安全系统的检测脚本实录

现代防指纹测绘脚本通常会采用如下异步侦测逻辑，只需 50 毫秒即可给出一个环境纯净度评分：

async function auditSpeechVoicesRisk() {
  const getVoicesAsync = () => new Promise(resolve => {
    let voices = window.speechSynthesis.getVoices();
    if (voices.length > 0) return resolve(voices);
    window.speechSynthesis.onvoiceschanged = () => {
      resolve(window.speechSynthesis.getVoices());
    };
    setTimeout(() => resolve(window.speechSynthesis.getVoices()), 800);
  });

  const voices = await getVoicesAsync();

  // ⚠️ 关键修正：只统计 localService === true 的本机离线引擎。
  // Edge 会通过 speechSynthesis 直接暴露整套 Azure 云端语音
  // （如 "Microsoft 晓晓 Online (Natural)"，localService === false），
  // 任何装了 Edge 的机器——包括美国本土的英文 Windows——都会列出这些名字。
  // 把它们当成“系统装了中文语音包”是最典型的误报来源。
  const localVoices = voices.filter(v =>
    v.localService === true && !/online|natural|google/i.test(v.name)
  );

  const chineseVoiceHits = localVoices.filter(v =>
    v.lang.toLowerCase().startsWith('zh') ||
    /Chinese|Huihui|Kangkang|Yaoyao|Hanhan/i.test(v.name)
  );

  const hasChineseVoice = chineseVoiceHits.length > 0;
  return {
    totalVoices: voices.length,
    localVoices: localVoices.length,
    cloudVoicesExcluded: voices.length - localVoices.length,
    chineseVoicesFound: chineseVoiceHits.map(v => v.name),
    isRiskDetected: hasChineseVoice,
    penalty: hasChineseVoice ? 10 : 0
  };
}

五、 常见伪装误区与错误手段

常见错误操作实际底层表现风控系统的反制逻辑
仅将浏览器界面语言设为英语navigator.language 变为 en-US，但 getVoices() 仍会列出中文发音人——其中大部分是 Edge 的云端语音改语言不会改变 localService === true 的本地引擎；但如果列表里只有云端语音，本身并不构成异常。
在油猴脚本中暴力覆写 window.speechSynthesis.getVoices = () => []直接返回空数组，且没有 SpeechSynthesisVoice 实例的原型链支持识别为“客户端反爬作弊（Script Tampering）”。真实桌面 Chrome 绝不可能有 0 个发音人。
通过非专业指纹浏览器伪装了英文发音人，但缺少系统原生私有属性伪造的虚拟发音人缺少 voiceURI 和原生 SpeechSynthesisVoice 类实例标识通过 Object.prototype.toString.call(voice) 秒破伪装，触发更严重的直接封禁。

六、 终极防御与彻底整改实操指南

要想彻底抹除 TTS 中文语音包泄露风险，必须从操作系统层面或通过高保真指纹隔离沙盒来进行物理级净化：

方案 A：macOS 只清理可下载的增强语音（系统内置语音删不掉）

  1. 打开 系统设置 → 辅助功能 → 朗读内容 → 系统语音 → 管理声音。
  2. 只处理你主动下载过的增强/高品质语音包（如「婷婷（增强）」「小美（增强）」）。
  3. 系统内置的基础语音（Ting-Ting、Mei-Jia 等）位于 /System/Library/Speech/Voices，受 SIP 保护，正常手段删不掉，也不必删——它们在每一台 Mac 上都有。
  4. 如果目的是减少环境信息量，优先处理时区、DNS、出口 IP 类型——这三项权重远高于语音。

七、 总结与自测建议

Web Speech API 确实能枚举宿主机语音，但它暴露的信息远比流传的说法少：平台内置语音是基线，Edge 的云端语音更是所有用户共享。真正值得关注的只有本机离线引擎那一小块，而且它只是弱信号，需要和时区、语言、IP 类型结合看。
