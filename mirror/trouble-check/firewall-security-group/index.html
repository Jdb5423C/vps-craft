1. 流量到达应用程序的三道关卡

当外部客户端向你的 VPS 发起 TCP 请求时，数据包必须依次通过以下三道防线才能抵达你的网站程序（Nginx / Docker / Node.js 等）：

第 1 道防线

云厂商外层网络安全组 (Cloud Security Group)

独立于 VPS 虚拟机操作系统之外，由云厂商（AWS / 阿里云 / 腾讯云 / 甲骨文云）的虚拟交换机（SDN）直接控制。如果这里的入站规则（Inbound Rules）没有放行端口，数据包连 VPS 的物理网卡都摸不到，在云厂商边界就被彻底丢弃！

第 2 道防线

宿主机本地系统防火墙 (UFW / Firewalld / Iptables)

运行在 Linux 内核层（Netfilter）。即使云安全组放行了，如果本地开启了 ufw 或 firewalld 且未添加相应的 allow 规则，内核会直接阻断该请求。

第 3 道防线

程序监听的 IP 地址 (127.0.0.1 vs 0.0.0.0)

应用程序（如 Node.js, Python Flask/FastAPI, MySQL）启动时如果监听的是 127.0.0.1，操作系统只会处理来自本机内部的请求；来自外网公网 IP 的请求会被直接拒绝（Connection Refused）！

2. 云厂商外层安全组配置要点 (重点防坑)

  • Oracle Cloud (甲骨文云 - 著名大坑)： 甲骨文不仅在控制台有 Security List（必须添加允许 TCP 0.0.0.0/0 规则），其官方 Ubuntu 系统镜像内部还预置了一套严格的 iptables DROP 规则！很多人在控制台放行了端口依然不通，就是因为被系统内预置规则拦截了。
  • 腾讯云轻量 / 阿里云 ECS： 创建实例时如果选择了“仅放行常用端口”或“Web 预设”，默认可能只开放了 80 和 443，自定义的高位端口（如 8080, 5432, 38222）必须在控制台“防火墙”手动添加规则。
  • AWS Lightsail / EC2： 进入实例详情 $\rightarrow$ 点击 Networking (网络) $\rightarrow$ 查看 IPv4 Firewall，确保有对应端口条目。

3. 宿主机本地防火墙排查与放行命令

① Ubuntu / Debian 系统：UFW 排查

查看 UFW 防火墙当前状态与已放行端口
bash
#如果 Status 为 active，请检查下方列表中是否有你的端口。
$sudo ufw status verbose
预期终端输出示例
Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), disabled (routed)
New profiles: skip

To                         Action      From
--                         ------      ----
22/tcp                     ALLOW IN    Anywhere
80/tcp                     ALLOW IN    Anywhere

如需开放常用端口或自定义端口：

一键通过 UFW 放行 SSH、HTTP、HTTPS 及指定端口
bash
#执行后即刻生效，不用重启 VPS。
$sudo ufw allow 22/tcp && sudo ufw allow 80/tcp && sudo ufw allow 443/tcp && sudo ufw reload

② CentOS / RHEL / AlmaLinux 系统：Firewalld 排查

Firewalld 放行端口并持久化重载
bash
#--permanent 确保 VPS 重启后规则依然保留。
$sudo firewall-cmd --zone=public --add-port=80/tcp --permanent && sudo firewall-cmd --zone=public --add-port=443/tcp --permanent && sudo firewall-cmd --reload

③ 甲骨文云 (Oracle Cloud) 预置 iptables 阻断救砖命令

⚠️ 甲骨文云用户必看： Ubuntu 镜像默认 iptables 会在所有规则末尾追加一条 REJECT。可运行以下命令放行全部入站流量（交由云控制台安全组管理即可）：
放行 Ubuntu 系统内部默认 iptables 限制
bash
#清空本地 iptables 规则链，让外层云安全组完全生效。注意：请先确认云控制台安全组已配置安全策略！
$sudo iptables -P INPUT ACCEPT && sudo iptables -P FORWARD ACCEPT && sudo iptables -P OUTPUT ACCEPT && sudo iptables -F

4. 致命的 127.0.0.1 监听误区：如何自查与修正

很多开发者在本地开发环境写习惯了 app.listen(3000, 'localhost') 或 server.bind(('127.0.0.1', 8000))，部署到 VPS 后发现外网无论如何都打不开！

检查当前所有正在监听的端口与绑定 IP
bash
#仔细检查第三列 Local Address:Port 的 IP 前缀。
$sudo ss -tlpn
预期终端输出示例
State   Recv-Q  Send-Q   Local Address:Port    Peer Address:Port  Process
LISTEN  0       128          127.0.0.1:3000             0.0.0.0:*      users:(('node',pid=456,fd=19))
LISTEN  0       511            0.0.0.0:80               0.0.0.0:*      users:(('nginx',pid=789,fd=6))
如何辨识：
  • 如果显示为 127.0.0.1:3000：仅允许本机内部回环访问！外网访客无法触达。
  • 如果显示为 0.0.0.0:3000 或 *:3000 或 :::3000：监听在所有网卡上，允许外网公网连接。
修正方案：将启动代码或配置文件中的 Host / Bind 地址从 127.0.0.1 或 localhost 改为 0.0.0.0，或通过 Nginx 进行反向代理暴露对外端口。
