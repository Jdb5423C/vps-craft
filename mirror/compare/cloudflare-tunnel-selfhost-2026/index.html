一、核心原理剖析：cloudflared 如何在 0 开放端口下实现穿透？

理解 Cloudflare Tunnel 的运行机制，对于后续排障和架构设计至关重要。传统反向代理（如直接在 Nginx 监听 80/443）属于入站连接模式（Inbound Connection）：公网客户端主动向你的服务器发起 TCP 握手，必须要求你的服务器拥有公网 IP，且沿途防火墙必须开放入站端口。

【传统模式 (Inbound)】:
外部访客 ──► [公网互联网] ──► 你的路由器/防火墙(暴露 80/443) ──► 源站 Web 服务器
(必须有公网 IP，端口完全暴露在互联网，常年遭受暴力扫描)

【Cloudflare Tunnel 模式 (Outbound-only)】:
外部访客 ──► [Cloudflare Anycast 边缘节点] (WAF清洗 + Zero Trust鉴权)
▲
│ 双向加密隧道 (基于 HTTP/2 或 QUIC 长连接)
│ (由 cloudflared 从内网主动向外发起，出站连接)
[你的内网 NAS / 廉价 VPS] ───┘
└─► cloudflared 守护进程 ──► 本地服务 (http://127.0.0.1:8080)
(无需公网 IP，入站端口全部为 0，防火墙进不去，物理隔绝公网扫描)

三大技术优势：

  • 单向出站连接（Outbound-Only）：cloudflared 本地守护进程启动后，会主动向最近的两个 Cloudflare 边缘节点发起 4 条并行的出站持久化连接（基于 QUIC/UDP 或 HTTP/2）。由于所有网络设备与路由器天然允许内部设备向外发起出站请求，因此完全不需要做任何端口映射或 UPnP 设置。
  • 源站物理隐身：外界没有任何办法直接探测到你服务器的真实 IP，因为你的主机在公网甚至连一个侦听端口都没有。任何企图直接扫描你 IP 的黑客都会收到连接拒绝。
  • 原生支持 Anycast 容灾：Cloudflare 负责接管全球 DNS 解析与 SSL/TLS 证书生命周期管理，访客永远连接最近的 Cloudflare 数据中心。

三、生产级实战教程：Linux systemd 与 Docker Compose 完整配置

生产环境必须采用 Named Tunnel（命名隧道），以确保在服务器重启、断网重连后依然稳定提供服务。以下为你提供业界标准部署流程：

1. 安装 cloudflared 官方客户端

BASH 
# Ubuntu / Debian
curl -fsSL https://pkg.cloudflare.com/cloudflare-main.gpg | sudo tee /usr/share/keyrings/cloudflare-main.gpg >/dev/null
echo 'deb [signed-by=/usr/share/keyrings/cloudflare-main.gpg] https://pkg.cloudflare.com/cloudflared jammy main' | sudo tee /etc/apt/sources.list.d/cloudflared.list
sudo apt update && sudo apt install -y cloudflared

# CentOS / RHEL
sudo dnf install -y https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-x86_64.rpm

# 验证安装版本
cloudflared --version

2. 登录授权与创建 Named Tunnel

SHELL / COMMAND 
# 1. 发起登录授权
cloudflared tunnel login
# 终端会输出一个授权 URL，复制到浏览器中打开，登录你的 Cloudflare 账户并选择你的域名进行授权。
# 授权成功后，会在本地生成证书文件：~/.cloudflared/cert.pem

# 2. 创建命名隧道（以 prod-vps-tunnel 为例）
cloudflared tunnel create prod-vps-tunnel

执行完成后，系统将输出一条关键信息：
Created tunnel prod-vps-tunnel with id 4a8b7c6d-1234-5678-9abc-def012345678
并在 ~/.cloudflared/ 目录下生成对应的凭证 JSON 文件：4a8b7c6d-1234-5678-9abc-def012345678.json。

3. 编写多域名 Ingress 路由配置文件（核心）

创建目录 /etc/cloudflared/，并编写生产级配置文件 /etc/cloudflared/config.yml：

SHELL / COMMAND 
tunnel: 4a8b7c6d-1234-5678-9abc-def012345678
credentials-file: /etc/cloudflared/4a8b7c6d-1234-5678-9abc-def012345678.json

# 传输协议配置（推荐采用 http2 模式以避开国内部分 UDP 阻断）
protocol: http2

ingress:
  # 1. 映射个人博客或主站应用
  - hostname: blog.yourdomain.com
    service: http://localhost:80

  # 2. 映射家庭 NAS 或私有云盘（如 Nextcloud）
  - hostname: pan.yourdomain.com
    service: http://localhost:8080
    originRequest:
      connectTimeout: 30s
      noTLSVerify: true

  # 3. 映射安全 SSH 终端（配合 Zero Trust 保护）
  - hostname: ssh.yourdomain.com
    service: ssh://localhost:22

  # 4. 【致命铁律】必须放置在末尾的兜底规则（未匹配域名返回 404）
  - service: http_status:404

⚠️ 致命避坑警告：Cloudflare Tunnel 的 Ingress 规则执行从上到下的顺序匹配，并且最末尾必须存在一条没有 hostname 的全局兜底规则（如 - service: http_status:404）！如果遗漏该兜底规则，cloudflared 校验配置时会抛出语法错误拒绝启动！

校验配置语法有效性：

SHELL / COMMAND 
cloudflared tunnel ingress validate

4. 配置 DNS CNAME 解析路由

无需手动去网页控制台添加解析，通过命令行一键完成 DNS 记录与 Tunnel 的联动：

SHELL / COMMAND 
cloudflared tunnel route dns prod-vps-tunnel blog.yourdomain.com
cloudflared tunnel route dns prod-vps-tunnel pan.yourdomain.com
cloudflared tunnel route dns prod-vps-tunnel ssh.yourdomain.com

Cloudflare 会自动在你的 DNS 面板创建指向 <Tunnel-UUID>.cfargotunnel.com 的 CNAME 橙色小云朵代理记录。

5. 方案 A：配置为 Linux systemd 开机自启服务（宿主机首选）

SYSTEMD 
# 将凭证复制到 /etc/cloudflared/ 目录
sudo cp ~/.cloudflared/*.json /etc/cloudflared/

# 安装为系统服务
sudo cloudflared service install

# 启动服务并设置开机自启
sudo systemctl daemon-reload
sudo systemctl enable --now cloudflared

# 检查运行状态与隧道连接
sudo systemctl status cloudflared

6. 方案 B：Docker Compose 一键启动配置（容器化首选）

如果你更喜欢纯 Docker 化运维，可以直接通过 docker-compose.yml 启动官方镜像：

DOCKER 
version: '3.8'

services:
  cloudflared:
    image: cloudflare/cloudflared:latest
    container_name: cloudflared-tunnel
    restart: unless-stopped
    command: tunnel run
    environment:
      - TUNNEL_TOKEN=eyJhIjoiY2... # 可以在 Zero Trust 后台直接复制 Token 启动，极简免挂载
    # 或者挂载本地 config.yml
    # volumes:
    #   - /etc/cloudflared:/etc/cloudflared
    # command: tunnel --config /etc/cloudflared/config.yml run
    network_mode: host # 推荐 host 网络模式，方便直接访问本机的 localhost 端口

四、Zero Trust (Cloudflare Access) 零信任企业级安全加固

把服务通过 Tunnel 穿透到公网后，许多人会感到担忧：“我的 NAS 面板、宝塔/1Panel、或内部 Wiki 系统密码被黑客暴力破解怎么办？”

这正是 Cloudflare 的杀手级功能——Zero Trust Access：在请求到达你服务器之前，必须先经过 Cloudflare 边缘设立的身份认证门禁！

1. 给敏感后台套上 Google / GitHub / Email OTP 验证

  1. 登录 Cloudflare Zero Trust 控制台（one.dash.cloudflare.com）。
  2. 进入 Access -> Applications，点击 Add an Application 并选择 Self-Hosted。
  3. 输入你的应用名称与受保护域名（例如 pan.yourdomain.com）。
  4. 配置 Policy（访问策略）：
    • Action: Allow
    • Include 规则：选择 Emails 并填入你的私人邮箱（例如 yourname@gmail.com），或者限制特定 Email Domain（如 @company.com）。
  5. 保存并生效。

实测防护效果：当任何外人尝试在浏览器打开 pan.yourdomain.com 时，他们连你的后台登录框都看不到，直接展示 Cloudflare 官方的验证界面，要求向你的专属邮箱发送一次性 6 位 PIN 码验证，或者通过绑定的 GitHub/Google 账户登录。黑客所有的漏洞扫描和暴力破解在此被 100% 物理拦截在边缘！

2. SSH 远程终端穿透：告别 22 端口暴露

很多开发者为了远程运维，被迫将 VPS 的 22 端口暴露在公网，每天遭受几十万次 SSH 密码字典撞库。配合 Cloudflare Tunnel，你可以彻底关闭 VPS 防火墙的 22 端口，通过浏览器或本地终端实现安全穿透：

  • 方式一：浏览器端直接 Web SSH。在 Zero Trust Access 应用配置中将类型选为 SSH，你可以在任何一台没有安装客户端的电脑上，通过浏览器网页直接打开一个加密的 Linux 命令行终端。
  • 方式二：本地终端通过 ProxyCommand 访问。在本地电脑安装 cloudflared，修改本地 ~/.ssh/config：
    SHELL / COMMAND 
    Host my-vps
  HostName ssh.yourdomain.com
  User root
  ProxyCommand cloudflared access ssh --hostname %h
    本地只需敲下 ssh my-vps，系统将自动唤起浏览器完成 Zero Trust 身份认证，随后直接建立安全的 SSH 会话！

五、6 大真实血泪避坑与性能调优指南

1. 默认 100MB 请求体积限制（大文件直传报错 HTTP 413）

现象与根源：Cloudflare 免费计划对所有通过 CDN 代理（包括 Tunnel）的 HTTP POST/PUT 请求设置了 硬编码的 100MB 单文件请求限制。如果你试图通过穿透的 Nextcloud 或网盘上传一个超过 100MB 的压缩包或视频，上传进度会在 100MB 时戛然而止，返回 HTTP 413 Payload Too Large。

解决策略：
1. 在网盘应用端启用分片上传（Chunked Upload），将大文件切分成 20MB~50MB 的小切片依次上传（如 Nextcloud 客户端默认支持切片）。
2. 超大文件传输走对象存储直传通道（如采用 Cloudflare R2 Presigned URL 客户端直传），完全绕过 Tunnel 隧道。

2. WebSocket 长连接断流与心跳保活

Cloudflare 边缘节点对空闲连接有 100 秒超时机制。如果你的穿透服务包含实时推送、实时聊天或 SSH 会话，只要客户端超过 100 秒无按键操作，隧道连接就会被边缘断开。在 /etc/ssh/sshd_config 中配置心跳参数即可彻底解决：

SHELL / COMMAND 
ClientAliveInterval 30
ClientAliveCountMax 3

3. 国内网络直连 cloudflared 握手延迟高问题排查

默认情况下，cloudflared 倾向于优先使用基于 UDP 的 QUIC 协议 建立与边缘节点的连接。但在国内很多省份，运营商会对国际出口的非标准 UDP 流量进行极其残酷的丢包限制（QoS 限速甚至直接阻断），导致 Tunnel 频繁断线重连、控制台大量打印 ERR failed to dial to edge。
优化手段：在 config.yml 中强制指定 protocol: http2，迫使 cloudflared 使用基于 TCP 的 HTTP/2 协议回源，稳定性将大幅提升。

4. 避免 Ingress 缺失兜底规则导致服务 Crash

再次强调，ingress 列表中务必以 - service: http_status:404 结尾。如果配置了错误的本地端口（例如本地服务未启动），建议在特定服务节点下加入 originRequest 的超时参数，避免单个不可达的服务阻塞整个隧道的事件循环。

5. TOS Section 2.8 合规红线

请勿通过 Cloudflare Tunnel 长期持续穿透分发海量侵权视频流或搭建 P2P 共享。如果单个免费 Tunnel 每月产生数 TB 纯视频流吞吐，可能会触发滥用审查。对于自用的家庭影音（如 Jellyfin/Emby），建议控制在外网偶尔播放，并开启硬编降码率。

6. 灾备多副本高可用 Connector 部署

一个 Named Tunnel 允许在不同的机器上运行多个相同的 cloudflared 进程（相同的 credentials-file）。这意味着你可以在同个局域网的两台设备（如一台 NAS + 一台软路由）上同时运行该隧道，当其中一台设备关机重启时，Cloudflare 会毫秒级将流量切换至另一台在线 Connector，实现 0 秒停机的无缝高可用！

常见热点问题解答 (FAQ)

Q1：使用 Cloudflare Tunnel 会扣费吗？

A1：完全免费！Cloudflare Tunnel 原本属于企业级 Argo 智能路由的高级功能，但官方早在 2021 年起便将其核心穿透功能面向所有免费用户完全免费开放，且不限隧道数量和基础带宽。

Q2：穿透之后，我怎么知道访客的真实 IP？

A2：流量经过 Cloudflare 节点转发后，真实客户端 IP 会被写入标准的 HTTP 请求头 CF-Connecting-IP 中。你的后端 Web 服务（Nginx/Node.js/Python）只需读取该头信息即可获取访客真实公网 IP。

Q3：为什么我穿透后访问速度比原来慢了？

A3：因为所有流量必须先经过 Cloudflare 位于海外或就近的 Anycast 节点清洗与解密，再由内网的 cloudflared 接收。对于中国大陆的访客，如果物理连接绕道美西节点，延迟会有所增加。Tunnel 的首要价值是“0 端口暴露的安全内网穿透与免公网 IPv4”，而非单纯的提速。
