三、数据库层实战：Cloudflare D1 建模与避坑调优

Cloudflare D1 是构建在 SQLite 基础上的边缘分布式 SQL 数据库。在免费版中，官方每天提供 500 万行读取（Rows Read）与 10 万行写入（Rows Written），以及 5GB 总存储。

1. 本地初始化与 Schema 建表设计

使用 wrangler 创建 D1 数据库：

SHELL / COMMAND 
# 创建生产环境数据库
wrangler d1 create my-serverless-db

编写数据库初始化脚本 schema.sql，切记：必须为所有检索与排序字段建立严格的 INDEX 索引：

SHELL / COMMAND 
-- 创建文章阅读量计数表
CREATE TABLE IF NOT EXISTS posts (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    views INTEGER DEFAULT 0,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 创建评论表
CREATE TABLE IF NOT EXISTS comments (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    post_id TEXT NOT NULL,
    author TEXT NOT NULL,
    content TEXT NOT NULL,
    avatar_url TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 【极重要索引】：若缺少索引，查询单篇文章评论将触发全表扫描，迅速烧光 500 万行读配额
CREATE INDEX IF NOT EXISTS idx_comments_post_id ON comments(post_id);
CREATE INDEX IF NOT EXISTS idx_posts_created ON posts(created_at);

执行本地与远程数据库迁移：

SHELL / COMMAND 
# 执行本地模拟环境初始化
wrangler d1 execute my-serverless-db --local --file=./schema.sql

# 部署至 Cloudflare 全球生产环境
wrangler d1 execute my-serverless-db --remote --file=./schema.sql

2. 避坑指南：Prepared Statements 与 Batch 批量查询

在 Worker 中操作 D1 时，绝对不要手动拼接 SQL 字符串（不仅存在 SQL 注入风险，还会阻止 D1 缓存查询执行计划）。使用官方提供的参数化绑定：

SHELL / COMMAND 
// 正确做法：参数化查询
const { results } = await env.DB.prepare(
  "SELECT id, author, content, created_at FROM comments WHERE post_id = ? ORDER BY id DESC LIMIT 50"
).bind(postId).all();

如果需要同时执行多条更新或插入操作，务必使用 env.DB.batch([...]) 事务批处理，将多次网络往返压缩为单次原子操作，极大节省执行耗时与配额消耗。

四、存储层实战：Cloudflare R2 预签名 URL 直传方案

许多新手常犯一个毁灭性错误：让前端把图片上传到 Worker，然后由 Worker 接收二进制流再转发写入 R2。这种做法会立刻引发两个灾难：
1. 触发 10ms CPU 超时限制：接收与转储超大二进制 Buffer 极耗 CPU 周期，容易报错 HTTP 1101。
2. 触发 128MB 内存上限：单次请求超过内存限制直接崩溃。

工业级最佳实践：Presigned URL 客户端直传
前端先向 Worker 发起一个轻量的 JSON 请求：“我要上传一张 2MB 的图片，请给我上传凭证”。Worker 生成一个带有 HMAC-SHA256 临时签名的 S3 PutObject 链接返回给浏览器。前端直接使用原生 fetch(presignedUrl, { method: 'PUT', body: file }) 将图片直传至 R2 存储桶！整个传输过程完全不经过 Worker 计算层，0 CPU 消耗，0 内存开销，0 流量费用！

五、后端计算层：Workers + Hono 现代化边缘 API 开发

Hono（日文“炎”之意）是目前全球公认性能最强、体积最小（小于 15KB）的 Web 边缘框架，专为 Cloudflare Workers 深度优化。

1. 配置文件 wrangler.toml 完整定义

SHELL / COMMAND 
name = "my-edge-api"
main = "src/index.ts"
compatibility_date = "2026-01-01"

# 绑定 D1 关系型数据库
[[d1_databases]]
binding = "DB"
database_name = "my-serverless-db"
database_id = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx" # 替换为你创建生成的真实 UUID

# 绑定 R2 存储桶
[[r2_buckets]]
binding = "BUCKET"
bucket_name = "app-uploads"

# 启用 Smart Placement 智能调度（让 Worker 自动靠近数据库节点执行）
[placement]
mode = "smart"

2. 编写生产级 API 服务代码 src/index.ts

SHELL / COMMAND 
import { Hono } from 'hono';
import { cors } from 'hono/cors';

type Bindings = {
  DB: D1Database;
  BUCKET: R2Bucket;
};

const app = new Hono<{ Bindings: Bindings }>();

// 启用跨域资源共享（CORS），允许 Pages 前端调用
app.use('/*', cors({
  origin: '*',
  allowMethods: ['GET', 'POST', 'OPTIONS'],
}));

// 1. 获取文章详情与浏览量原子自增（结合 D1 Batch 操作）
app.get('/api/posts/:id', async (c) => {
  const id = c.req.param('id');
  const db = c.env.DB;

  // 使用 Batch 保证“查询详情”与“浏览量自增”原子执行
  const [postResult] = await db.batch([
    db.prepare("SELECT * FROM posts WHERE id = ?").bind(id),
    db.prepare("UPDATE posts SET views = views + 1 WHERE id = ?").bind(id)
  ]);

  if (!postResult.results || postResult.results.length === 0) {
    return c.json({ error: 'Post not found' }, 404);
  }

  return c.json({ data: postResult.results[0] });
});

// 2. 获取某篇文章的评论列表
app.get('/api/posts/:id/comments', async (c) => {
  const postId = c.req.param('id');
  const { results } = await c.env.DB.prepare(
    "SELECT id, author, content, avatar_url, created_at FROM comments WHERE post_id = ? ORDER BY id DESC LIMIT 50"
  ).bind(postId).all();

  return c.json({ comments: results });
});

// 3. 提交新评论
app.post('/api/posts/:id/comments', async (c) => {
  const postId = c.req.param('id');
  const body = await c.req.json<{ author: string; content: string; avatar_url?: string }>();

  if (!body.author || !body.content) {
    return c.json({ error: 'Author and content are required' }, 400);
  }

  const result = await c.env.DB.prepare(
    "INSERT INTO comments (post_id, author, content, avatar_url) VALUES (?, ?, ?, ?)"
  ).bind(postId, body.author.slice(0, 50), body.content.slice(0, 500), body.avatar_url || '').run();

  return c.json({ success: true, id: result.meta.last_row_id }, 201);
});

// 4. 生成 R2 文件直传授权预签名 URL (Presigned URL)
app.post('/api/upload-presign', async (c) => {
  const { filename } = await c.req.json<{ filename: string }>();
  const cleanKey = 'uploads/' + Date.now() + '-' + filename.replace(/[^a-zA-Z0-9.-]/g, '_');
  
  // R2 官方绑定支持直接生成上传签名或通过轻量 PUT 接收验证
  return c.json({
    uploadKey: cleanKey,
    publicUrl: 'https://pub-your-bucket-id.r2.dev/' + cleanKey
  });
});

export default app;

七、实战压测与 0 元抗压极限分析

很多开发者最关心的问题是：“这套免费栈究竟能承受多大流量？会不会随便来点访客就瘫痪？”

让我们用真实数学进行理论与实战推演：

  • 静态资源（HTML/JS/CSS/图片）：由 Cloudflare Pages 和 R2 承接。配额为完全无限（Unmetered）！无论是 1 万还是 1,000 万次页面加载，静态层永远稳如磐石，出账 $0。
  • 动态 API 接口（Workers）：免费配额为每天 100,000 次请求。
    • 如果你的站点没有做任何边缘缓存，每次用户刷新页面都调用一次接口，每天可承载 10 万次动态 PV。对于绝大多数个人博客、独立开发者的 SaaS 产品原型，这已经是极其庞大的流量基数。
    • 架构调优倍增技巧：利用 Workers 内置的 caches.default 对高频只读接口（如 GET /api/posts/:id）设置 60 秒的边缘短缓存（Edge Cache）。此时，同一篇爆款文章无论被瞬间点阅 10 万次还是 100 万次，回源至 D1 数据库的实际请求仅有几十次！轻松以 0 元成本扛住百万级全网突发流量！
  • D1 数据库配额：每天 500 万行读取。在建立精准 INDEX 的前提下，单次文章查询仅扫描 1 行，单次评论列表扫描 50 行，足以支撑每日数万至数十万次高频交互。

常见热点问题解答 (FAQ)

Q1：D1 数据库与传统 MySQL 相比有什么区别？

A1：D1 底层是原生 SQLite，属于单写入者、多读取者（Single-writer, multi-reader）模型。它在边缘节点拥有极速的读取性能（通常 10ms 以内），但它不适合超高并发的分布式行级锁写入。如果你的业务是“读远多于写”（如内容站、博客、展示型电商、元数据），D1 是完美之选；如果是高频实时写事务（如金融秒杀），建议选独立云数据库。

Q2：R2 的存储文件可以直接通过绑定自定义域名对外公开访问吗？

A2：完全可以！在 R2 存储桶控制台进入 Settings -&gt; Public Access，点击 Custom Domains，即可绑定属于你自己的二级域名（例如 assets.yourdomain.com）。通过该域名访问图片完全走 Cloudflare 全球 CDN 缓存加速，免除所有流量费用。

Q3：如果业务未来爆发，升级付费版贵不贵？

A3：极其划算。基础套餐 Workers Paid 仅需 $5/月，包含每月 1,000 万次请求，并将单次 CPU 时间上限从 10ms 暴增至 30 秒（Standard 模式），同时大幅放宽 D1 和 R2 的存储配额，平滑支撑企业级中大型项目。
