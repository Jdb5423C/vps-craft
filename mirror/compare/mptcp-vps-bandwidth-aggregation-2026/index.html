家里拉了两条宽带，一条电信一条联通，下载却永远跑不满？或者你在海外，想回国访问看看爱优腾，单线延迟高得能泡面？很多人听说 MPTCP 能"把两条宽带叠成一条"，但网上教程要么太学术、要么只扔一个脚本就完事。这篇就把 MPTCP 这件事讲透：它到底解决什么问题、你的 VPS 要怎么选、OpenMPTCProuter 怎么落地，以及那些一踩一个准的坑。

MPTCP 到底是什么，和 BBR 是一回事吗？

先把这个最常见的误会掐死：MPTCP 和 BBR 不是一类东西，别混着比。BBR 是 Google 在 2016 年提出、从 Linux 4.9 起内置的单路径拥塞控制算法，它干的事是"测出瓶颈带宽和最小延迟，然后决定这条连接该发多快"，专门治弱网和高延迟下的吞吐与延迟抖动。CUBIC 是看丢包定速，BBR 是看模型定速，就这么点区别。

MPTCP（Multipath TCP）则完全在另一层。它是 IETF 标准化的 TCP 扩展（RFC 6824，2020 年修订为 RFC 8684），让一条 TCP 连接能同时跑在多条网络路径上。比如你手机连着 Wi‑Fi 又开着蜂窝，MPTCP 可以让同一条连接的两个"子流（subflow）"分别走 Wi‑Fi 和 4G，带宽叠加、还能一条断了另一条无缝顶上。iPhone 从 2013 年的 Siri 就开始这么干了。

两者的正确关系是"互补可叠加"，不是二选一。有论文专门研究用 BBR 作为 MPTCP 各子流的耦合拥塞控制（Leveraging Coupled BBR and Adaptive Packet Scheduling to Boost MPTCP, TWC 2021），OpenMPTCProuter 社区也建议在"网络到 MPTCP"这一层把拥塞控制切成 bbr2。一句话总结：BBR 解决"单线怎么跑得稳"，MPTCP 解决"多线怎么并成一条"。

内核与启用：Linux 5.6+ 原生支持，VPS 必须 KVM

好消息是 MPTCP 早就不用打补丁了。Linux 内核从 5.6 版（2020 年）起原生内置 MPTCP（编译选项 CONFIG_MPTCP=y），Ubuntu 22.04+、Debian 12+、Fedora 36+ 这些主流发行版默认就带。所以你不用折腾内核补丁，只要确认内核够新。

落地前先在自己机器和 VPS 上各敲几条命令自测：

  • uname -r 看内核是不是 ≥ 5.6；
  • sysctl net.mptcp.enabled 应该返回 1；
  • cat /proc/sys/net/mptcp/enabled 输出 1 即开启；
  • ip mptcp limits show 看子流数量上限；
  • ip mptcp endpoint add 10.0.0.5 dev eth1 subflow 把第二条链路加为子流；
  • 用 ss -tinm 观察是否真的建立了多个子流。

关键点：VPS 必须能改内核，也就是 KVM、Xen HVM 这类全虚拟化环境。OpenVZ、LXC、纯 Docker 容器通常改不了内核、加载不了 MPTCP 模块，直接出局。这也是为什么聚合端点得是一台正经 KVM VPS，而不是那种白菜价的 OpenVZ 小鸡。

让普通应用也走多路径：mptcpize 与调度器

这里有个反直觉的坑：内核开着 MPTCP，但你的 curl、wget、nginx 默认还是走普通 TCP，因为它们没主动建多子流。想让普通程序用上 MPTCP，有几种办法：

  • 用 mptcpize run -- curl https://example.com，这是 LD_PRELOAD 方式强行给程序套上 MPTCP；
  • Go 语言程序设 GODEBUG=multipathtcp=1（Go 1.21+ 支持）；
  • 内核 6.6+ 可以用 eBPF 工具 mptcpify-bpfcc 按 cGroup 强制一组进程走 MPTCP；
  • 验证站点：check-mptcp.dev 或 check-mptcp.io 能直接告诉你当前连接有没有走多路径。

另外 MPTCP 还能选调度器（scheduler），决定流量往哪条子流塞：

  • default：均衡使用所有子流，有线链路常用；
  • bleed：把流量优先引向延迟低的路径，无线/高丢包链路（比如 4G/5G）常用，命令是 sysctl -w net.mptcp.mptcp_scheduler=bleed；
  • backup：主路径正常时不用，只有主路径挂了才顶上，适合做故障转移。

实测里经常会遇到"明明两条线，下载只跑了一条"——往往就是调度器没配对，或者应用没被 mptcpize 包裹，只建了单子流。

OpenMPTCProuter：把两条宽带叠成一条的家庭方案

如果你是想把家里的多条宽带聚合成一条，而不是在服务器之间搞事情，那 OpenMPTCProuter（简称 OMR）是最省心的全家桶。它基于 OpenWrt，架构分两端：

  • 本地网关：一台软路由（树莓派、友善 NanoPi、x86 小主机都行），多 WAN 口分别插电信、联通、4G/5G；
  • 远端 VPS 汇聚节点：所有出网流量经加密隧道（Glorytun / Shadowsocks / V2Ray 等）送到这台 VPS，由 VPS 作为单一出口把多条子流"汇合"，对外看起来就是一条大宽带。

VPS 端装起来很简单，官方 Debian 脚本一行搞定：

  • wget -O - https://www.openmptcprouter.com/server/debian-x86_64.sh | KERNEL="6.12" sh
  • 装完后密钥存在 /root/openmptcprouter_config.txt，必须 reboot 让新内核生效；
  • 再到本地路由器向导里填 VPS 的 IP 和那串密钥，等隧道握手成功即可。

注意那个 KERNEL="6.12" 参数是让脚本给你装好自带 MPTCP 的 6.12 内核，省得你自己折腾。脚本来自 OMR 官方文档镜像，照抄即可。

VPS 选什么：聚合端点就是一台能换内核的便宜 KVM

说破天，OMR 的 VPS 端就是"一台能换 6.x 内核的便宜 KVM VPS"，它本身不是什么特殊商品，用常规低价 VPS 就够。挑的时候盯三个点：

  • 能改内核：必须 KVM，别买 OpenVZ/LXC；
  • 延迟越低越好：VPS 到本地各条线路的延迟直接决定聚合后的体验，节点尽量选离你近的；
  • 出口带宽要高于你聚合后的总带宽：否则 VPS 先成瓶颈，叠了也白叠。

具体到本站的白名单厂商，这几个很合适做聚合端点：

  • Bandwagon（搬瓦工）：KVM、年付 40 美元以上档位，线路更稳，适合对稳定性要求高的场景；

一个容易忽略的提醒：VPS 的月流量上限要能装下你聚合后的总出网量。多线叠加后流量涨得飞快，如果是 1TB 封顶的小鸡，回家下一个大电影可能就把额度吃没了。

真实聚合效果与硬件瓶颈

MPTCP 真能把两条宽带叠加吗？能，但有前提。有实测案例是 DSL + Starlink + LTE 三线聚合，一开始只走主线路，后来把"默认代理"改成"替代传输协议"并且如实填了每条 WAN 的合同带宽，下载才真正达到理论聚合值。也就是说，配置对了才叠加，配置错了就退化成单线。

带宽叠加之外还有个卖点：故障转移。主线路断了，子流自动切到备线，正在下的文件、正在开的视频不至于断。对单线稳定性差的环境（比如小运营商、弱网回国）价值很大。

但硬件是有天花板的：

  • 树莓派 4 在 150–180Mb/s 以下很轻松，再往上 CPU 和网卡就吃力了；
  • 想跑更高带宽，建议上 x86_64 软路由并带 AES‑NI 指令集，加密隧道才不卡；
  • 千兆网卡本身就是上限，别指望百兆口叠出千兆。

部署最常见的坑

把社区里踩烂的坑集中说一遍，能省你一下午：

  • VPS 和某条 WAN 同网段：会导致 IP 冲突甚至路由环路，拓扑上避开；
  • 买了不支持换内核的 OpenVZ：MPTCP 模块加载不了，白搭；
  • 装完没 reboot：新内核没生效，配置全不灵，OMR 脚本明确要重启；
  • 流媒体被封：所有流量经 VPS 隧道后，公网 IP 变成了数据中心 IP，Netflix、Disney+、Apple TV+ 这类常封机房 IP。OMR 提供 OMR Bypass，可以让指定域名（比如流媒体）走原始 WAN 的真实 IP；
  • 树莓派成为高带宽瓶颈：想跑超过 180Mb/s，直接上 x86_64 + AES‑NI。

另外提醒一句：所有走 VPS 隧道的流量，公网出口都是 VPS 的 IP。如果你本来是想"回国加速"，那 VPS 得选能解锁国内服务的节点；如果是为了"出海"，那 VPS 的地理位置又得反过来选。目的不同，节点选法完全相反。

常见热点问题解答 (FAQ)

MPTCP 和 BBR 有什么区别？

不在同一层。BBR 是单连接的拥塞控制算法，决定"发多快"；MPTCP 是多路径传输协议，决定"走哪几条路"。两者不冲突反而能叠加——让 MPTCP 的各子流用 BBR 作拥塞控制会更稳。BBR 解决弱网单线吞吐，MPTCP 解决多线聚合与故障转移。

用 VPS 做 MPTCP 聚合要什么内核？

客户端和服务器端内核都得 ≥ 5.6（2020 年起原生支持），建议上 6.x。OMR 官方脚本可用 KERNEL="6.12" 直接装好带 MPTCP 的内核。VPS 必须是 KVM 等可改内核环境，OpenVZ/LXC/Docker 不行。

MPTCP 真的能把两条宽带叠加快吗？

能，但有限制。第一，两端都要支持 MPTCP，普通应用得用 mptcpize 包裹；第二，单条大下载能被多子流拆分而叠加，但很多 App 默认只建单子流需手动强制；第三，聚合上限受 VPS 出口带宽和到本地延迟约束；第四，配置错（代理协议、IP 冲突）会导致只走主线路。

哪类人适合用 MPTCP / OpenMPTCProuter？

多 WAN 家庭（光纤+4G/5G+Starlink）、回国/弱网加速、对单线稳定性要求高需故障转移的人。单线 VPS 用户、只想给单一连接提速的普通用户，收益非常有限。

MPTCP 部署最常见的坑是什么？

① VPS 与 WAN 同网段导致 IP 冲突/路由环路；② 用了不能换内核的 OpenVZ；③ 装完没 reboot 导致不生效；④ 流媒体因数据中心 IP 被封（用 OMR Bypass 解决）；⑤ 树莓派网卡/CPU 成为高带宽瓶颈（>180Mb/s 建议 x86_64 + AES‑NI）。
