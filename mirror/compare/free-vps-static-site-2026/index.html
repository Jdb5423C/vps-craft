一、动静分离整体架构蓝图：让 99% 请求在边缘命中

[外部访客 Request] │ ▼ [Cloudflare Anycast 边缘节点] ───► 是否有边缘缓存? ├─────────►【命中 HIT (99% 请求)】──► 0ms 边缘直接返回浏览器 (0 消耗源站流量!) │ └─────────►【未命中 MISS / 动态请求】 │ ▼ [Cloudflare Tiered Cache (上层数据中心汇聚)] │ ▼ [源站 VPS (Nginx / Caddy)] ──► 仅处理 1% 的动态接口与初次回源 │ ▼ (返回并携带强效 Cache-Control 响应头) [Cloudflare 自动在边缘缓存] ──► 供后续全球数万次请求直接复用

核心设计哲学：

  • 资源分级治理：将静态指纹文件（带有 hash 后缀的 JS/CSS/图片）设置为 1 年永久不可变缓存（immutable）；将半动态内容（博客 HTML、商品展示页）设置为短 TTL 结合 stale-while-revalidate 异步刷新。
  • 源站物理防火墙兜底：只允许 Cloudflare 官方公布的回源 IP 段访问 VPS 的 80/443 端口，杜绝攻击者通过绕过 CDN 旁路直连源站扫爆 VPS 出站带宽。

二、源站 Web 服务器配置：Nginx 生产级缓存头实战

Cloudflare 边缘 CDN 的缓存行为完全受源站返回的 HTTP 响应头驱动。如果你的源站 Nginx 没有正确声明 Cache-Control，Cloudflare 会采用默认保守策略（例如默认完全不缓存 HTML 内容）。

1. Nginx 生产级站点配置 /etc/nginx/conf.d/mysite.conf

NGINX 
server {
    listen 80;
    listen 443 ssl http2;
    server_name example.com;

    # SSL 证书配置（使用 Let's Encrypt 或 Cloudflare Origin CA）
    ssl_certificate /etc/nginx/ssl/example.com.crt;
    ssl_certificate_key /etc/nginx/ssl/example.com.key;

    root /var/www/html;
    index index.html index.htm;

    # =========================================================================
    # 1. 静态指纹资源（JS/CSS/字体/图片）：极致不可变缓存 1 年
    # =========================================================================
    location ~* .(?:ico|css|js|gif|jpe?g|png|webp|avif|svg|woff2?|eot|ttf|mp4)$ {
        try_files $uri =404;
        
        # 强制设置 1 年长效缓存，immutable 指明内容永不更改（若代码更新文件名会带新 hash）
        add_header Cache-Control "public, max-age=31536000, immutable" always;
        
        # 允许跨域（方便字体和图床加载）
        add_header Access-Control-Allow-Origin "*";
        
        # 关闭静态资源访问日志，极大减少 VPS 磁盘 I/O 开销
        access_log off;
    }

    # =========================================================================
    # 2. 纯动态 API 接口：绝对禁止缓存
    # =========================================================================
    location /api/ {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        # 强制告知边缘与浏览器不进行任何缓存
        add_header Cache-Control "no-store, no-cache, must-revalidate, proxy-revalidate, max-age=0" always;
    }

    # =========================================================================
    # 3. 半动态 HTML 页面（核心黑科技：Stale-While-Revalidate）
    # =========================================================================
    location / {
        try_files $uri $uri/ @backend;
        
        # 边缘缓存 60 秒；过期后的 1 小时内，访客仍瞬间拿到旧缓存，Cloudflare 在后台异步回源更新！
        add_header Cache-Control "public, max-age=60, stale-while-revalidate=3600" always;
    }

    location @backend {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        
        # 同样输出 SWR 响应头
        add_header Cache-Control "public, max-age=60, stale-while-revalidate=3600" always;
    }
}

2. 深度拆解：为什么必须使用 stale-while-revalidate？

在传统的缓存体系中，一旦缓存过期（max-age 到期），下一个访问该页面的“倒霉访客”必须在屏幕前死等你的源站 VPS 生成并返回最新内容，如果遇到服务器高负载，响应会卡顿数秒。

而在开启 stale-while-revalidate=3600 后：
1. 访客永远 0 延迟：缓存过期后，首个到访的用户依然毫秒级拿到旧的缓存页面，完全感知不到等待。
2. 异步非阻塞回源：Cloudflare 边缘节点在把旧数据返回给访客的同时，在后台悄悄向你的 VPS 发起一次回源请求，获取最新 HTML 并更新边缘缓存。
3. 彻底杜绝缓存穿透雪崩（Cache Stampede）：即便文章瞬间被 10,000 人同时刷新，也只有后台那 1 次异步回源会打到源站 VPS，其余 9,999 人全部由边缘缓存承接！

三、Cloudflare 边缘控制台调优（Cache Rules 实操）

自 2023 年起，Cloudflare 正式弃用了陈旧的 Page Rules（页面规则），全面升级为现代化的 Cache Rules（缓存规则）。请在 Cloudflare Dashboard 中完成以下三项黄金配置：

1. 免费开启 Tiered Cache（分层缓存）

操作路径与界面辨析（免费用户实操指引）：
• 新版控制台路径：进入域名面板 -> 左侧导航栏 Caching（缓存） -> Tiered Cache（分层缓存）。
• 旧版控制台路径：若没有独立子菜单，进入 Caching（缓存） -> Configuration（配置） -> 向下滚动找到 Tiered Cache 模块。
• 免费版界面开关说明：在免费计划（Free Plan）下，控制台不会提供多拓扑下拉选择框（那是 Enterprise 版用于选择 Custom 拓扑的高级选项）。免费用户看到的是一个极简的 切换开关（Toggle Switch 开关）。只需将 Tiered Cache 开关直接点亮开启（切换为 On），Cloudflare 就会在底层自动且唯一启用 Smart Tiered Cache（智能分层缓存）！如果你的源站托管在 AWS、GCP 或 Oracle Cloud，还可以在下方的 Origin Configuration 中选填 Cloud Region Hint（云区域提示）。
技术原理：Cloudflare 全球拥有 330 多个边缘数据中心。在默认关闭时，每一个边缘节点未命中缓存都会各自独立向你的 VPS 回源一次。开启分层缓存后，Cloudflare 会在核心枢纽设立统一的“中枢缓存层”。边缘节点未命中时，先向上层中枢询问，中枢也没有才回源。实测直接降低源站 VPS 回源流量 60% 以上！且此功能对所有免费用户永久免费！

2. 配置全站 HTML 缓存 Cache Rule

默认情况下，Cloudflare 是绝不缓存 HTML 页面的。要实现全站近乎 0 流量，必须配置一条 Cache Rule：

  1. 进入 Caching -> Cache Rules -> 点击 Create rule。
  2. 规则命名：Cache-HTML-SWR。
  3. 匹配条件（When incoming requests match）：
    (http.request.uri.path does not start with "/api/" and http.request.uri.path does not start with "/admin" and http.request.uri.path does not start with "/wp-admin")
  4. 缓存设置（Cache eligibility）：勾选 Eligible for cache（允许缓存）。
  5. Edge TTL：选择 Respect origin cache-control header（遵循源站设置的 SWR 头）。
  6. Browser TTL：选择 Respect origin cache-control header。
  7. Serve stale content while revalidating：保持勾选开启。
  8. 点击 Deploy 保存生效。

3. 配置 Cache Response Rules 自动清除意外的 Set-Cookie 响应头

很多开源博客（如 WordPress、Typecho）会在返回文章 HTML 时顺手带上一个空的 Set-Cookie 头。在默认规则下，任何带有 Set-Cookie 响应头的请求都会被 Cloudflare 强制放弃缓存！这是很多人配了半天缓存依然回源率 100% 的终极隐形杀手！

解法：在 Caching -> Cache Response Rules 中创建规则，对非后台页面执行 Remove header: Set-Cookie，确保纯展示型页面能够被边缘无障碍永久缓存。

四、源站安全防御：Linux UFW 防火墙仅允许 Cloudflare IP

如果黑客直接扫描你的真实 VPS IP（通过旁路扫描工具或全网 IPv4 探测），你的 VPS 依然会被直接打爆。必须在操作系统内核防火墙上，将 80 和 443 端口的所有流量封锁，只放行 Cloudflare 官方公布的回源 IP 段！

2. UFW 一键白名单脚本（杜绝绕过 CDN 直连源站）

在 VPS 上保存并执行以下 Bash 脚本：

BASH 
#!/bin/bash
# 确保 SSH 端口开放（切勿锁死自己！）
sudo ufw allow 22/tcp

# 默认关闭所有入站连接
sudo ufw default deny incoming
sudo ufw default allow outgoing

# 从 Cloudflare 官方拉取最新 IPv4 网段并添加到 UFW 白名单
curl -s https://www.cloudflare.com/ips-v4 | while read ip; do
  if [ -n "$ip" ]; then
    sudo ufw allow proto tcp from $ip to any port 80,443 comment 'Cloudflare IPv4'
  fi
done

# 启动防火墙
sudo ufw enable
sudo ufw reload

安全验证：执行完毕后，你在本地浏览器直接在地址栏敲入 https://你的VPS公网IP，会立刻遭到 ERR_CONNECTION_TIMED_OUT 丢包拦截；而通过域名访问网站则一切丝滑流畅！任何黑客的直接扫描工具在此被 100% 物理丢弃，你的 VPS 流量账单得到了绝对安全保障。

五、自动化运维：版本更新与 Cache Purge API

当你在源站发布了一篇新文章或修改了前端布局，由于边缘设置了强效缓存，外部访客可能无法立刻看到更新。如何做到“发布即生效”？

利用 Cloudflare Purge API 实现自动化清除缓存：
无需每次手动登录网页控制台。在你的博客发布脚本或 Git Webhook 中加入一条简单的 curl 命令：

BASH 
# 针对特定修改的 URL 单独清除缓存（推荐做法，不影响全站其他缓存）
curl -X POST "https://api.cloudflare.com/client/v4/zones/<ZONE_ID>/purge_cache" \
     -H "Authorization: Bearer <YOUR_API_TOKEN>" \
     -H "Content-Type: application/json" \
     --data '{"files":["https://example.com/posts/my-new-article"]}'
