# 一、为什么不能调太快？深入 OCI 的底层风控与限流机制

很多新手误以为“请求发得越快，抢中概率越高”，甚至有人将脚本直接写成 while true; do curl ...; sleep 1; done。在甲骨文云上，这种做法极容易导致账户直接被封。

# 1. HTTP 429 TooManyRequests 错误

根据 Oracle 官方 API 错误指南 与 OCI 速率限制文档：

  • OCI API 对资源创建类的写操作（Write Operations，如 LaunchInstance）设有严格的每分钟请求配额（通常单 IP / 单租户每分钟允许的写请求在几十次以内）；
  • 如果请求过频，服务端会立即拦截并返回 HTTP 429 TooManyRequests，请求根本不会真正递交到底层资源调度器；
  • 部分 SDK（如 Go/Python SDK 或 OCI-CLI）在遇到 429 或 500 错误时，如果不关闭重试，会开启内置的指数退避（Exponential Backoff）机制，导致单次请求挂起数十秒才结束。

# 2. 甲骨文风控审计：高频 API 触发滥用（Abuse）

甲骨文的风控系统对纯免费租户（Always Free）有严格的行为基线检测。如果一个没有任何付费记录的新租户，以秒级频率向同一 API 节点不间断发送数万次失败的开机请求，会被安全系统判定为“恶意 DoS / API 滥用（Resource Abuse）”，从而直接进入封号（Termination）黑名单。

# 二、主流开源脚本的默认机制与社区实战数据

通过审视 GitHub 知名开源项目的源码，可以观察到专业开发者对间隔时间的权衡：

# 1. 经典之作：hitrov/oci-arm-host-capacity

由前甲骨文高级工程师 Alexander Hitrov 开源的 oci-arm-host-capacity（Star 1.3k+）是全网使用最广的脚本之一：

  • 官方推荐方案：采用系统底层 Crontab 驱动：
BASH 
  # 官方推荐的 Crontab 示例：每 1 分钟执行一次
  * * * * * /usr/bin/php /path/to/oci-arm-host-capacity/index.php >> /path/to/oci.log 2>&1
  • 实际使用反馈：在 Reddit r/oraclecloud 社区的长期测试中，不少用户反馈如果在单可用域（Single AD）每 1 分钟固定打卡，某些高峰期偶发出现过 Too many requests，随后社区普遍调整为 每 2 分钟一次（*/2 * * * *），长期运行非常稳定，无一例因频率问题被封禁。

# 2. 容器化方案：mowirth/oci-instance-creator

在 mowirth/oci-instance-creator 的环境参数定义中：

BASH 
# 全局轮询周期，默认 60 秒
CREATE_INTERVAL_SECONDS=60
# 跨多个可用域（Availability Domain）时，每个区之间的缓冲等待，默认 10 秒
CREATE_ZONE_SECONDS=10

该项目明确强调，即便在同一周期内，对不同可用域（AD-1、AD-2、AD-3）也必须强制增加 10 秒等待，防止并发突发请求击穿 OCI 防护网。

# 3. 退避机制方案：gamer995/oracle-arm-hunter

在面向 Linux Systemd 守护进程的开源项目 gamer995/oracle-arm-hunter 中，作者引入了企业级退避参数：

TEXT 
RETRY_INTERVAL=300 # 默认每 300 秒（5分钟）正常重试一次
BACKOFF_INITIAL=5 # 遭遇限流初始等待 5 秒
BACKOFF_MAX=60 # 遭遇限流最大指数退避 60 秒

# 三、科学抢机的关键技巧：如何兼顾速度与安全性？

单纯缩减间隔时间并不能保证抢到机器，反而容易招致风控。结合社区成功经验，以下四项策略能显著提升成功率：

# 1. 引入随机抖动时间（Jitter）

固定且毫无偏差的请求间隔（例如精准的每 60.000 秒执行一次）极易被云厂商防火墙判定为机器人行为。 最佳实践是在固定休眠基础上，加入一个 0 到 30 秒的随机延时：

BASH 
#!/bin/bash
# 科学轮询示例：基础 60 秒 + 随机 0~30 秒浮动
while true; do
    echo "[$(date)] 尝试发起创建请求..."
    # 调用 OCI 命令 (关闭内置指数退避以节约无谓挂起)
    oci compute instance launch --cli-options-here ...
    
    # 生成 0~30 之间的随机数
    SLEEP_RANDOM=$((RANDOM % 31))
    SLEEP_TOTAL=$((60 + SLEEP_RANDOM))
    echo "本次请求结束，休眠 ${SLEEP_TOTAL} 秒后进行下一轮..."
    sleep ${SLEEP_TOTAL}
done

# 2. 巧用 --no-retry 提升轮询效率

默认情况下，OCI CLI 在遇到服务器端报错（如 500 InternalError / 无容量）时，会自动进行指数重试，导致这一轮请求卡死等上一两分钟。 在脚本中调用 OCI CLI 时，建议显式加上 --no-retry 参数，把等待控制权留给自己的脚本：

BASH 
OCI_FLAGS=(--no-retry --connection-timeout 10 --read-timeout 45)
oci compute instance launch "${OCI_FLAGS[@]}" ...

这样一旦机房返回“无容量”，脚本会立即获取结果并进入由用户掌控的安全休眠阶段，杜绝不可控的长时间卡顿。

# 3. 规格降级拆分：别死磕 4C + 24G

许多用户脚本挂了几个月毫无动静，主要原因在于：一次性要求机房空出“连续 4 个完整核心 + 24GB 内存”的物理宿主机空位难度极高。

  • 建议策略：
    • 先将脚本目标设为 1 OCPU / 6GB 内存 或 2 OCPU / 12GB 内存；
    • 小规格资源在宿主机母鸡中更容易“见缝插针”，成功率通常比直接拉满 4C24G 高出数倍；
    • 等第一台机器成功开机后，后续可以在控制台直接热升级配置，或者再开第二台分担算力。

# 4. 多可用域（Availability Domain）轮换

对于拥有多个可用域的区域（如美西凤凰城、法兰克福、伦敦等），必须让脚本在 AD-1、AD-2、AD-3 之间轮流切换，而不是死盯某一个分区。往往 AD-1 爆满的时候，AD-2 就有少量资源释放。

# 四、终极解决之道：升级 PAYG（随用随付）降维打击

如果你已经挂了几个星期的脚本仍然一无所获，必须认识到甲骨文云底层的资源优先级分配规则：

TEXT 
[ 官方底层资源池放货分配优先级 ]
  ❶ 付费企业合约用户 (Enterprise)
  ❷ 绑定信用卡升级的 PAYG 随用随付用户 (Pay As You Go)  <-- 优先级高
  ❸ 纯免费账户 (Always Free 免费试用/未升级用户)         <-- 优先级极低
  • 免费额度依然有效：账户升级为 PAYG（随用随付）后，ARM 4C24G 和 200GB 硬盘的免费配额完全保留不变，只要不超标，账单依然是 $0.00；
  • 拥有更高的调度权限：当宿主机腾出少量 A1 容量时，系统会优先满足 PAYG 用户的创建请求；
  • 开机成功率极高：在 NodeSeek 社区的大量反馈中，许多用户在免费层挂机一个月无果，升级为 PAYG 后的当天甚至手动点击即可直接开通。

# 五、总结与操作红线

  1. 时间间隔红线：
    • 绝对不要低于 30 秒一次，否则必定面临 429 报错与被风控风险；
    • 最佳推荐值设定为 60 秒 ~ 120 秒，并显式加入 10~30 秒的随机休眠（Jitter）；
  2. 账号资产安全第一：
    • 抢机脚本必须运行在干净独立的 VPS 或本地终端上，严禁滥用 GitHub Actions 公共工作流无休止运行（已有多起因滥用公共算力触发 GitHub 封号的案例）；
    • 切勿为了追求速度而并发多开几十个脚本轰炸同一租户，平稳、低调、模拟正常调用，才是安全拿下永久免费甲骨文云主机的关键所在。
