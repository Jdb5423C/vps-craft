在跨国网络传输中，数据包往往要漂洋过海穿越太平洋或欧亚大陆，遇到公网高峰期极易产生偶发丢包。传统 TCP 算法（如 CUBIC 或 Reno）一旦遇到丢包，就会误以为网络发生了严重堵塞，进而自废武功般地把发送速率直接砍半（断崖式降速）。

而 Google 开发的 BBR（Bottleneck Bandwidth and RTT）拥塞控制算法，彻底改变了这一机制：它通过精确测量实时物理带宽管道容量和数据往返时延（RTT），不再将单次丢包作为降速的唯一依据，即使在高丢包的恶劣跨境网络环境下，也能让 VPS 的网络吞吐与视频加载速率提升数倍甚至数十倍。

本文先教你如何 100% 准确核验 BBR 是否已开启且生效，随后针对不同系统和网络环境，提供 4 种由浅入深的开启方案，彻底解决脚本失效或老旧内核无法启用的困扰。

# 一、怎么 100% 确认 VPS 是否开启了 BBR？（逐行读懂终端输出）

要彻底确认 BBR 的运行状态，核心是检查三个环节：内核是否支持、算法是否选定为当前默认、以及配套的发包队列规则（qdisc）是否正确。

以下是真实生产环境中一台标准配置、完全正常生效的 VPS 终端回显样本：

BASH 
[root@vps ~]# uname -r
5.15.60-1.el7.x86_64

[root@vps ~]# lsmod | grep bbr
tcp_bbr                20480  14 

[root@vps ~]# sysctl net.ipv4.tcp_congestion_control
net.ipv4.tcp_congestion_control = bbr

[root@vps ~]# sysctl net.ipv4.tcp_available_congestion_control
net.ipv4.tcp_available_congestion_control = reno cubic bbr

[root@vps ~]# sysctl net.core.default_qdisc
net.core.default_qdisc = fq

# 逐项拆解判断逻辑：

  1. uname -r $\rightarrow$ 内核版本必须 $\ge$ 4.9
    • BBR 自 Linux Kernel 4.9 版本起被官方正式合入主线内核。
    • 如果返回的是 5.15.xx、6.1.xx 或更高，说明系统内核原生自带 BBR；如果版本低于 4.9（如原生 CentOS 7 的 3.10.0），则必须先升级内核。
  2. lsmod | grep bbr $\rightarrow$ 模块是否加载进内存
    • 回显 tcp_bbr 20480 14：表示 tcp_bbr 内核模块已正确加载；后面的数值 14 是模块引用计数，代表当前系统正有活跃的网络套接字/连接在使用该算法。
    • (注：部分专门编译的精简内核直接将 BBR 内置编入内核静态镜像而非作为动态模块加载，此时 lsmod 可能为空，最终仍以第 3 步 sysctl 为准)。
  3. sysctl net.ipv4.tcp_congestion_control $\rightarrow$ ★ 最核心的生效标准
    • 输出必须等于 bbr！
    • 如果返回 cubic 或 reno，即便系统支持，当前传输也并未实际享受到 BBR 的加速红利。
  4. sysctl net.ipv4.tcp_available_congestion_control $\rightarrow$ 可选算法列表
    • 输出列表中必须包含 bbr（如 reno cubic bbr），说明系统环境已被允许调度 BBR。
  5. sysctl net.core.default_qdisc $\rightarrow$ 队列调度规则
    • 官方建议必须搭配 fq（Fair Queue，公平队列）。fq 能够平滑突发流量数据包的发送节奏（Pacing），这是发挥 BBR 极致性能的黄金搭档。

# 进阶验证：查看具体网络连接是否正在使用 BBR

如果想看实时连接层面的加速状态，可以在终端执行：

BASH 
ss -tin

在输出的连接统计中，如果能看到类似 bbr:(bw:94.2Mbps,mrtt:125.4,pacing_rate:113Mbps) 字样，则 100% 说明具体连接正在通过 BBR 进行流量整型与拥塞控制。

# 二、方案一（首选纯净）：现代系统原生两行命令开启（免脚本/免换内核）

适用环境：所有 Linux 内核 $\ge$ 4.9 的发行版（包括 Debian 10/11/12、Ubuntu 20.04/22.04/24.04、CentOS Stream 8/9、AlmaLinux、Rocky Linux 等）。

现代主流 Linux 系统早已自带 BBR 模块，根本不需要下载来路不明的第三方脚本，更不需要冒险换内核，只需写入系统配置即可生效：

BASH 
# 1. 确保以 root 用户执行，将配置写入系统底层参数
echo "net.core.default_qdisc=fq" >> /etc/sysctl.conf
echo "net.ipv4.tcp_congestion_control=bbr" >> /etc/sysctl.conf

# 2. 刷新并立即应用配置
sysctl -p

# 规范化标准（推荐写入独立配置文件）：

在较新的 Debian / Ubuntu 系统中，更推荐将参数写入 /etc/sysctl.d/ 独立目录，避免后续系统升级覆盖主配置文件：

BASH 
sudo bash -c cat > /etc/sysctl.d/99-bbr.conf << EOF
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr
EOF

# 重新加载所有 sysctl 规则
sudo sysctl --system

执行完毕后，直接敲 sysctl net.ipv4.tcp_congestion_control 即可见证其变为 bbr。

# 三、方案二（经典一键脚本）：老旧系统换内核多合一加速（CentOS 7 原生 3.10 等）

如果你的 VPS 仍然安装了比较古老的系统（如原生 CentOS 7 默认锁死在 3.10 内核），原生命令无法生效，此时借助社区成熟的自动化换内核脚本是最省力的方式。

# 1. 经典纯净版：秋水逸冰（Teddysun）一键 BBR 脚本

这是开源社区维护时间最长、口碑最稳定的标准 BBR 安装脚本，支持 CentOS 6+、Debian 7+、Ubuntu 12+ 自动检测并拉取最新稳定内核：

BASH 
wget --no-check-certificate -O bbr.sh https://github.com/teddysun/across/raw/master/bbr.sh
chmod +x bbr.sh
./bbr.sh
  • 执行过程：脚本会自动下载并安装适配的官方新内核，安装完成后提示 Do you want to restart system? [y/n]，输入 y 重启机器；
  • 重启后：脚本已自动持久化配置，重新连上终端执行 sysctl net.ipv4.tcp_congestion_control 即已生效。

# 2. 综合进阶版：ylx2016 / Linux-NetSpeed 多合一加速脚本

在技术论坛（NodeSeek、HostLoc）中被广泛使用的网络加速集合工具，集成了原版 BBR、BBRplus、BBRv3、锐速以及内核卸载管理：

BASH 
# 不卸载内核版本（安全推荐）
wget -O tcpx.sh "https://github.com/ylx2016/Linux-NetSpeed/raw/master/tcpx.sh" && chmod +x tcpx.sh && ./tcpx.sh
  • 交互菜单中输入对应编号：
    • 先选择安装内核（如安装官方 BBR 内核或 BBRplus 内核）；
    • 重启后再次运行 ./tcpx.sh，选择对应算法的“开启加速”即可。

# 四、方案三（极客前沿）：升级 XanMod 内核开启 Google BBRv3

适用场景：追求极致低延迟与抗丢包表现、使用 Debian 11/12 或 Ubuntu 22.04/24.04 的 KVM 虚拟机。

Google 近年对 BBR 算法进行了大幅重构并演进到了 BBRv3，相比初版 BBR，它显著降低了网络队列积压（Bufferbloat），在弱网丢包环境下的带宽恢复效率更加迅猛。 知名调优内核项目 XanMod 已官方合入了 Google BBRv3 代码，通过其官方 APT 仓库即可一键升级：

BASH 
# 1. 导入 XanMod 官方 GPG 密钥
wget -qO - https://dl.xanmod.org/archive.key | sudo gpg --dearmor -vo /usr/share/keyrings/xanmod-archive-keyring.gpg

# 2. 注册官方源
echo 'deb [signed-by=/usr/share/keyrings/xanmod-archive-keyring.gpg] http://deb.xanmod.org releases main' | sudo tee /etc/apt/sources.list.d/xanmod-release.list

# 3. 更新源并安装最新 XanMod 内核（支持 x86-64-v3 或常规通用版）
sudo apt update && sudo apt install -y linux-xanmod-x64v3

# 4. 重启实例
sudo reboot
  • 说明：重启后，系统内核将变为 XanMod 编译版；由于内核已深度集成 BBRv3，直接应用原生命令 sysctl -w net.ipv4.tcp_congestion_control=bbr，此时内核底层跑的便已是前沿的 BBRv3 逻辑。

# 五、方案四（备用兜底）：脚本失效/网络超时？纯手动升级内核（以 CentOS 7 为例）

很多时候，国内网络或特定机房由于 GitHub Raw 域名被Q或 SSL 报错，常常导致一键脚本下载失败（Connection refused 或 404 Not Found）。掌握纯手动升级内核与启用 BBR 的能力，是运维人员的必备底气。

以最容易卡在 3.10 内核的 CentOS 7 为例，通过官方镜像源 ELRepo 手动升级：

BASH 
# 1. 导入 ELRepo 官方公钥与仓库 RPM 包
rpm --import https://www.elrepo.org/RPM-GPG-KEY-elrepo.org
rpm -Uvh https://www.elrepo.org/elrepo-release-7.el7.elrepo.noarch.rpm

# 2. 安装长期支持版（kernel-lt）或主线版（kernel-ml）新内核
yum --enablerepo=elrepo-kernel install -y kernel-lt

# 3. 检查已安装内核并设置默认从新内核引导
grub2-set-default 0
grub2-mkconfig -o /boot/grub2/grub.cfg

# 4. 重启服务器
reboot

重启完成后：

  1. 运行 uname -r，确认内核已成功跨入 5.x 或 6.x 时代；
  2. 再运行前文方案一的两行命令写入 /etc/sysctl.conf 并 sysctl -p，即可大功告成！

# 六、疑难排查与避坑指南（为什么你的 BBR 还是打不开？）

如果在配置过程中遇到报错，对照以下四条红线进行快速排查：

# 1. 虚拟化架构死穴：LXC 与 OpenVZ 容器小鸡

  • 如果你的 VPS 是几块钱买的 LXC 或 OpenVZ 架构小鸡，由于它与宿主机母鸡共享同一个内核，你没有独立修改内核参数的权限；
  • 执行 sysctl -p 时往往会直接报错 sysctl: cannot stat /proc/sys/net/ipv4/tcp_congestion_control: No such file or directory 或 Permission denied；
  • 解决办法：容器架构无法自主换内核，如需使用 BBR，必须选择 KVM 架构 的全虚拟化 VPS！

# 2. 重启后 BBR 自动失效，退回 CUBIC？

  • 出现这种情况，通常是因为某些一键面板（如老版本宝塔、某些安全防护软件）或系统初始化脚本在开机时强制覆写了网络参数；
  • 检查指令：
BASH 
  grep -rn "tcp_congestion_control" /etc/sysctl.conf /etc/sysctl.d/

检查是否有多个配置冲突。删除冲突的 cubic 字段，确保仅保留 net.ipv4.tcp_congestion_control = bbr 这一项。

# 3. 模块未自动挂载？

如果在 sysctl -p 时提示未找到算法，可以手动先将模块注入内核：

BASH 
sudo modprobe tcp_bbr
echo "tcp_bbr" | sudo tee -a /etc/modules-load.d/modules.conf
